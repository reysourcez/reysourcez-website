# Form Scanner — change notes

(Covers `form-scanner.html` / `.js` / `-proxy-worker.js`. Kept as a separate file from `FORM_SCANNER_SETUP_AND_GLOSSARY.md`, same split Costing Analysis uses between its own change notes and its stable reference doc — the glossary describes how things work *now*; this file is the history of *why*.)

## 2026-09-22 — Site-integration rebuild, orientation/size detection, richer structure, color toggle

**What prompted this.** A separate session had asked Gemini directly to fix and extend the scanner. It produced a working "v4.3 default best" build that genuinely scanned both images and PDFs into editable PDFs — a real capability gain — but with its own standalone inline theme (no site nav, no `AI_BUILD_BRIEF.md` conventions, no `styles.css`) since it didn't have those docs in context, and no real orientation/size detection: a reported case had an A5-landscape source PDF (Lampiran 6 — Resit Rasmi) come back out as A4 portrait. This round's brief: bring the working parts back onto the site's own architecture, verify the Gemini model choice against current docs rather than assume it, detect the source's actual size/orientation and match it by default, push structural fidelity further ("as detailed as possible" — exact rows/columns, not an approximation), add a note-driven way to force a different output size/orientation/font, and make fillable fields colorless by default with an explicit opt-in for shading.

**Verified before touching the Worker, not assumed.** Fetched Google's current Gemini API docs directly. Two things confirmed: `gemini-flash-lite-latest` is a real, current, auto-updating `-latest` alias (Google's own docs give `gemini-flash-latest` as the worked example of this exact naming pattern for a model tier) — kept as-is rather than pinning a dated model string, since Google's own deprecation schedule is aggressive (`gemini-2.5-flash-lite` shuts down Oct 16 2026, `gemini-2.0-flash-lite` already gone). And the classic `generateContent` endpoint this Worker uses is explicitly still Google's own recommended path for production, in Google's own words: *"While it is now considered legacy, the original generateContent API remains fully supported"* and, on the newer path, *"we will continue to actively develop and maintain [generateContent]... For production workloads, you should continue to use the standard generateContent API."* This also explains something already sitting in the original Worker file's own header comment: an earlier attempt at Google's newer "Interactions API" shape caused errors and was reverted back to `generateContent`. That wasn't a wrong guess — Google's current docs still flag Interactions as `"currently in Beta. Features and schemas are subject to breaking changes"` for at least some of its surface. Reverting was correct then and staying on `generateContent` is correct now.

**What was fixed from the Gemini-built v4.3 round.** Not a rewrite-from-scratch — the working scan/build pipeline was kept, but a few real regressions from that round (it didn't have this site's other files in context) are restored:
- CORS fallback was `'*'` (any origin) when the request's Origin didn't match the allowlist; restored to the original's safer fallback (the first allowed origin).
- `thinkingConfig: { thinkingLevel: 'low' }` had been dropped entirely — restored. This is the exact fix `food-worth-proxy-worker.js` already needed once before (3-series models default to a slow "high" thinking level otherwise); dropping it silently reintroduces the risk of slow/timed-out scans.
- The usage-cap pattern (`MAX_SCANS_PER_DAY`, localStorage) that every other tool on this site shares had been dropped; restored.
- `recognized` was trusted at face value from the model's own JSON; restored the original's belt-and-suspenders re-check (re-derive it from whether anything was actually extracted).
- pdf-lib was loaded from `unpkg` instead of this site's established `cdnjs` convention; switched back.
- **Kept, as a genuine improvement:** the top-level try/catch wrapping the whole Worker `fetch` handler, so an unexpected error still comes back as clean JSON rather than a bare 500.

**New: orientation + page-size detection, client-side.** Two different sources of truth, deliberately:
- A real uploaded PDF has its exact page size read directly via pdf-lib (`PDFDocument.load` → `getPage(0).getSize()`) — no guessing, which is the direct fix for the Lampiran 6 bug above.
- A photo has no true physical page size, only pixels — orientation is read from the image's own natural width/height (reliable, no AI needed), and the paper *size* falls back to Gemini's best-effort `page_size_guess` (or plain A4 if it's unsure).

Both feed `resolvePageGeometry()`, which also applies any explicit override from the note (see next). The resolved size/orientation is shown in the results panel *before* download ("Output will be A5 landscape…") so a wrong guess is obvious immediately rather than discovered after opening the file.

**New: `render_directives` — the "AI prompter" for forcing a different output.** The existing note field now does double duty: structure guidance (as before) *and* an explicit ask about the output itself — a different page size, orientation, font (Helvetica/Times/Courier — the three StandardFonts pdf-lib can embed without a custom font file), or bigger/smaller text. Gemini reads the note and returns `render_directives` populated **only** when something was explicitly asked for; every field defaults to "keep the source's own" otherwise. This was built as an AI-interpreted free-text field rather than a set of dropdowns because "make this A5 landscape with a bit more room" reads more naturally than picking three separate controls — the tradeoff is it rides on the same Gemini call rather than being instant/client-side, which felt like the right trade for something that's more request-like than setting-like.

**New: real orientation/size scaling.** Rather than a hardcoded A4-vs-A5 binary, font size/margins/row heights all scale together via one factor computed from the *area* of the resolved page relative to A4 — same area as A4 (e.g. A4 landscape) scales 1×, half the area (A5, either orientation) scales to ≈0.71× (this reproduces what was previously a hardcoded 0.707 constant for A5 specifically, but now generalises to A3/Letter/Legal/custom PDF sizes too), and anything bigger than A4 is capped at 1× rather than scaled up.

**New: meaningfully richer structure, still schema-guarded.** Every addition below is optional with a safe fallback in the sanitizer, so a model response that gets one wrong degrades gracefully rather than breaking the scan — deliberately not a jump to a fully generic nested schema, since an earlier, more ambitious round reportedly stopped scanning reliably and was abandoned:
- `column_groups` — genuine two-row table headers (a group label spanning several sub-columns, e.g. "TUNAI" over "Masuk"/"Keluar" — this exact pattern shows up in the Lampiran 5 Buku Tunai example already on file). Falls back to an ordinary single-row header if the spans don't add up.
- `columns_width_pct` — the model's estimate of each column's relative width, so a narrow "Bil." column and a wide "Perkara" column come out looking proportioned like the source instead of split evenly. Falls back to the old header-text-length heuristic if missing/invalid.
- `column` on header fields and signature blocks — side-by-side layouts (a payment-voucher's left/right header, three signature blocks in a row — again, a real pattern in the Lampiran 5 example) instead of everything forced into one stacked column. Generalises what the Gemini build had already introduced as a hardcoded left/right split.
- Real checkbox AcroForm fields for tick-box choices (e.g. a payment-method row), replacing static `[ ] Label` bracket text that wasn't actually clickable in either earlier build.
- `reference_tables` — already-printed lookup/threshold tables (not something to fill in), rendered as plain text in a bordered grid rather than turned into blank fields.
- `subtitles`, `footnotes`, `amount_in_words_label` — carried over from the Gemini build's own additions, which were reasonable generalisations of the original's title/reference_code-only shape.

**Real bug fix, not just a new feature: table borders across a page break.** Both earlier builds computed a table's outer border as one rectangle sized from the *assumed* total row count, drawn once after the row loop. If a table happened to split across a page break, that assumption breaks — the rectangle would be drawn at the wrong height against whatever's on the second page. This round draws every border segment incrementally (per header block, per row) instead, so pagination naturally produces a correctly-scoped grid on both pages with no special-casing needed. Fixed once at the table level and reused as the same pattern for reference tables.

**New: field-color toggle, default off.** A checkbox ("Shade fillable fields with a light tint") on the upload panel, unchecked by default. pdf-lib only writes a field's background when `backgroundColor` is actually passed to `addToPage()` — confirmed again this round that leaving it out entirely (the default state) means no `/MK /BG` entry at all, not a pale color that merely looks white. When checked, the tint used matches the site's own `--accent-soft` token rather than an arbitrary color, so it stays visually consistent with the rest of the site if anyone does turn it on.

**Considered and *not* adopted this round: `baidu/Unlimited-OCR`.** Checked directly rather than going on the description alone. It's real and well-regarded (26k GitHub stars, MIT licensed, in the DeepSeek-OCR lineage of vision-language document-parsing models) — but it isn't a small/lightweight model in a deployable sense: every inference path shown (Transformers, vLLM, SGLang) requires an NVIDIA GPU, CUDA, and a full Python ML stack (`torch`, `transformers`, `pymupdf`, etc.), served either self-hosted or via Docker on GPU infrastructure. That's a fundamentally different, ongoing-cost operational commitment than this site's current "GitHub Pages + Cloudflare Workers, no server, near-zero hosting cost" architecture, which `AI_BUILD_BRIEF.md` states as a non-negotiable. Beyond the infrastructure mismatch, it also solves a different problem than what this tool needs from Gemini: its output is raw parsed text with position tags (`<|det|>category [bbox]<|/det|>content`), not a ready-made "this is a table header, this is a fillable field" semantic JSON — Gemini's structured-output feature is what currently skips that whole extra interpretation step. Where it *would* be genuinely relevant: the KIV around column widths/group spans being estimates rather than true measured bounding boxes. If pixel-exact positioning ever becomes a priority, a specialised layout model like this is the right category of tool to revisit — but only as a deliberate infrastructure decision (a GPU-backed backend is real, ongoing money), not something to fold in quietly.

## 2026-09-23 — First real-world test results: two bugs fixed

**What prompted this.** Direct test results against the previous round's build, using the actual Baucar Bayaran (Lampiran 8) and Resit Rasmi (Lampiran 6) forms this whole project has been using as reference cases throughout. Two distinct problems, reported together but genuinely separate:

**Bug 1 — stale upload preview.** After scanning a photo, then uploading a different PDF, the old photo's preview image stayed on screen instead of switching to the new file's own preview — even though the scan itself correctly read the new file (right orientation, right structure). Root cause: `.fs-preview-img { display: block; ... }` and `.fs-pdf-preview { display: flex; ... }` in `form-scanner.html` are class selectors with the same CSS specificity as the browser's own built-in `[hidden] { display: none }` rule, and they load later — so they were silently winning the cascade, and toggling the `hidden` property in JS stopped actually hiding either element visually. Fixed with an explicit `.fs-preview-img[hidden], .fs-pdf-preview[hidden] { display: none; }` rule (higher specificity, so it always wins regardless of source order).

**Bug 2 — real structural regression, not a false alarm.** Reported: roughly 30% structural resemblance to source, against "roughly 90%" for the Gemini-built v4.3 this round's rebuild was based on — and specifically, a two-column signature layout (Disediakan oleh on the left; three separate Disemak dan diluluskan oleh blocks stacked on the right) came back rendered as one long stacked column instead. Diagnosis: v4.3's schema forced this decision by using separate, mandatory arrays (`header_left`/`header_right`, `left_signatures`/`right_signatures`) — the model had no way to avoid deciding what went where. The previous round's schema generalised this into a single `column` number to support more than two columns, but left it **optional**, defaulting to 1 (i.e. "everything stacked") whenever the model didn't bother setting it. More flexible in principle, measurably less reliable in practice for exactly the document family this tool is actually being used on — the same shape of tradeoff this project's own history already flagged once for an overly-ambitious schema round.

Two changes, not one, since a second, smaller instance of the same root problem was found on closer inspection: checkbox-choice fields (e.g. `KAEDAH PEMBAYARAN` / payment method, which sits inline within the Baucar Bayaran's right-hand column) were always rendered in a separate full-width pass *after* every plain field, regardless of which column they actually belonged to — so even a field with its column set correctly could still land in the wrong place on the page.

Fixes:
- `column` is now a `required` field in the schema for both `header_fields` and `signature_blocks` items — Gemini's structured-output mode enforces `required` at the API level, so the model can no longer silently omit it. (The sanitizer's clamp-and-default-to-1 fallback stays as a safety net for a malformed response, but should now rarely be the thing actually deciding the layout.)
- The prompt gained a dedicated instruction — not just a per-field schema description — telling the model to actively check each field's and each signature block's horizontal position against its neighbours before deciding on column, with the exact Baucar Bayaran/Resit Rasmi-style patterns (a payment-voucher header, multiple stacked sign-off blocks beside a single one) as worked examples, since those are literally the forms this is being tested against.
- `form-scanner.js`'s header-field rendering was unified: one column-aware loop now handles plain fields and checkbox-choice rows together, in their real order within each column, instead of two separate passes (plain fields, then all checkbox fields pushed to the end).

**Honest framing, not just a fix.** Building on Gemini's codes and then generalising their schema for more flexibility was the right instinct for handling form types beyond this one family, but it traded away reliability on the exact forms already in active use, and the evidence for that is now concrete rather than theoretical. The richer schema (column groups, relative widths, reference tables, etc.) added in the previous round stays — none of it was implicated in this specific regression — but `column` specifically needed to go from "optional, nice when the model provides it" back to something closer to v4.3's "the schema won't let you dodge this," which is what it is now.
